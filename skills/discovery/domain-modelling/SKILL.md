# domain-modelling

Status: implemented; the operational workflow is available.

Before execution, read its [contract](../../../contracts/skills/domain-modelling.md) for inputs, outputs, constraints, gates and failure behaviour.

Consult the [manifest](../../../manifest/skills.json) for invocation and dependencies, the [shared skill contract](../../../contracts/skill-contract.md) for composition, the [artifact contract](../../../contracts/artifacts.md) for persistence, and [routing rules](../../../contracts/routing.md) for prerequisites.

## Workflow

1. Read the specification or the decision set, and the project context. A glossary entry is not a decision and does not by itself justify a domain model. Never copy secret values; record only their existence and architectural effect. Record blockers through step 6 and continue; the only BLOCKED return is step 8.
2. When project context is missing, record that blocker and recommend `context-engineering`. Do not run that skill and do not add it as a dependency.
3. A domain model can be written only when a specification or a decision set has status `ready`. One `ready` input is enough. The other input being absent does not block. When neither input is `ready`, record a blocker and name every missing or non-ready prerequisite. Recommend the earliest blocker: a decision-set problem before a specification problem. A missing, `draft`, `blocked` or `superseded` decision set, while no specification is `ready`, recommends `clarify`. Recommend `to-spec` only when the specification is the earliest remaining blocker.
4. Model only when the `ready` input involves business terminology, invariants, state transitions, business events or context boundaries. A change the `ready` input limits to CRUD or infrastructure, or that does not involve those concerns, does not justify a model. Record that outcome as a blocker, introduce no DDD construct, and recommend `architecture-design` when R9 applies to that input, otherwise `to-tickets`.
5. Do not invent a business or architectural decision. When a material ambiguity, a premise that can still change the model, or a conflict with an existing decision appears, record a decision blocker that recommends `clarify`. Preserve the existing decision. Keep a premise labelled as a premise; it does not become a concept, relationship or invariant. Leave a rejected alternative out of the model. When an external fact can still change the model, record an external-fact blocker that recommends `research`. Do not access the network and do not add a dependency.
6. Do not reopen a question that the `ready` input, repository evidence or project context already answers. Limit language, concepts, relationships, invariants, transitions, events, boundaries and ambiguities to those inputs. When the `ready` input names no transition, event, or context boundary, record that absence and cite the input. Do not fill the gap with an example. Include an optional DDD section only when the `ready` input already justifies that construct.
7. When no blocker remains, write one domain model for that objective under `.ai/artifacts/domain/`, using the existing template and frontmatter and including every required section. Set status `ready`. That ready domain model is the only file this skill writes. Do not leave template draft markers. List the consumed artifact identifiers in `inputs`. On a later execution of the same objective, update that same file and increment `version`. The objective is the objective of the `ready` specification or, when no specification is `ready`, the objective of the `ready` decision set. The domain model that already cites that input is the model for that objective. Do not create a duplicate. When the consumed inputs are unchanged, keep the material sections, status and recorded model unchanged.
8. When any blocker remains, write no file. Return one BLOCKED report with `Status: BLOCKED`, `Reason`, `Evidence`, `Missing prerequisite` and `Recommended next skill/action`, and name every missing prerequisite. `Evidence` cites the input for each blocker. Recommend the skill for the earliest blocker, in this order: missing project context, then a decision-set problem, then a specification problem, then an external fact, then a change that does not justify a model.
9. Stop. When a domain model was written, report its path, status and whether the requested next step is authorized. A `ready` domain model authorizes the next step whose existing routing prerequisite is a ready domain model. Recommend at most the first applicable skill: `architecture-design` when R9 applies, otherwise `to-tickets`. When the requester did not ask for a step beyond the model, report that it is `ready` and which downstream consumer the canonical sequence would indicate. Do not invoke the recommended skill. Do not write the glossary, `CONTEXT.md`, any other artifact, or extend ADR `0001`.

## Failure behaviour

Return the [contracted `BLOCKED` result](../../../contracts/failure.md) when any blocker remains. Name every missing prerequisite. `Evidence` cites the input for each blocker. Recommend the earliest blocker: missing project context recommends `context-engineering`; a decision-set problem recommends `clarify`; a specification problem recommends `to-spec`; an external fact recommends `research`; a change that does not justify a model recommends `architecture-design` when R9 applies and otherwise `to-tickets`. Do not leave a domain-model file. The only file this skill writes is a ready domain model. Never present the BLOCKED result as a ready domain model.
