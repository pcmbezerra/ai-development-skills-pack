# implement

Status: implemented; the operational workflow is available.

Before execution, read its [contract](../../../contracts/skills/implement.md) for inputs, outputs, constraints, gates and failure behaviour.

Consult the [manifest](../../../manifest/skills.json) for invocation and dependencies, the [shared skill contract](../../../contracts/skill-contract.md) for composition, the [artifact contract](../../../contracts/artifacts.md) for persistence, and [routing rules](../../../contracts/routing.md) for prerequisites.

## Workflow

1. Read the project context and every defining input that is present: a ticket, a specification, a diagnosis report and an explicit change request. A glossary entry is not a change request and does not by itself authorize a change. Never copy secret values; record only their existence and effect. Record blockers through step 6 and continue; the only BLOCKED return is step 8.
2. When project context is missing, record that blocker and recommend `context-engineering`. Do not run that skill and do not add it as a dependency.
3. Apply a change only for the objective the requester named. A ready ticket with bounded scope and measurable acceptance criteria is that objective when the requester names the ticket; do not implement any other ticket. A ready diagnosis whose root cause is confirmed and whose recommended fix is bounded is that objective when the requester names the diagnosis. An explicit change request is that objective when the desired behaviour is clear and the scope is bounded; a specification is not required for that request. A ready specification is that objective only when it names one bounded change with testable acceptance criteria. A ready specification that still needs decomposition, or that contains more than one independent change, does not authorize implementing the specification as a set.
4. When the named ticket is absent or a present ticket has any status other than `ready`, record a ticket blocker that recommends `to-tickets`. When the named specification is missing, `draft`, `blocked` or `superseded`, and no ready ticket and no clear bounded explicit request define the same objective, record a specification blocker that recommends `to-spec`. When a diagnosis is present and the root cause is not confirmed, or the cause of a failure is unknown, record a diagnosis blocker that recommends `diagnose`. Do not modify code to discover a cause. When no defining input exists, or the explicit request is not clear or not bounded, record a decision blocker that recommends `clarify`.
5. Use a research report as evidence only when its status is `ready`. When a present research report has any other status, or an external fact can still change the change, record an external-fact blocker that recommends `research`. Do not access the network and do not add a dependency. A recommendation in a ready research report becomes part of the change only when the defining input already adopted it.
6. Do not invent behaviour, a decision or a fix. When a material ambiguity, a premise that can still change the change, or a conflict with an existing decision appears, record a decision blocker that recommends `clarify`. Preserve the existing decision. Keep a premise labelled as a premise. Leave a rejected alternative out of the change. Do not reopen a question that the defining input, repository evidence or project context already answers. Limit the change, the report and the test evidence to those inputs. When the ready input names no content for a required report or evidence section, record that absence and cite the input. Do not fill the gap with an example. The smallest correct change excludes unrelated edits and speculative abstractions. When keeping the change smallest still requires an unrelated edit or a speculative abstraction, record that gate blocker.
7. When no blocker remains and the implementation gate passes, apply the smallest correct change for that objective in the working tree. Do not write a `CHANGE_SET` file and do not invent a schema or template for it. The working-tree change is the named-only change set, and the report cites it as `working tree`. Write one implementation report for that objective under `.ai/artifacts/implementation/`, using the existing template and frontmatter and including every required section. Set status `ready` and `created_by` to `implement`. Write one test-evidence file for that objective under `.ai/artifacts/tests/`, using the existing template and frontmatter and including every required information section. Set status `ready` and `created_by` to `implement`. Do not leave template draft markers. List the consumed artifact identifiers in `inputs`. On a later execution of the same objective, update those same two files and increment `version`. The report that already cites that objective is the report for it. Do not create a duplicate. When the consumed inputs are unchanged, keep the material sections and the recorded change unchanged and do not apply the change again. When the inputs change, apply only the additional smallest change and update the same files. If a relevant test fails, revert the change from this attempt and treat the gate as failed. An unknown cause recommends `diagnose`. Do not delete an existing report or test-evidence file. The files this skill writes are the ready implementation report and the ready test evidence. When a test harness already exists, include the relevant test in the smallest change and record its result. When no harness exists, record that absence in the test evidence and validate the change by the check the input named. When R11 applies, record that `tdd` applies and was not invoked. The existing optional dependencies stay. This recommendation does not add a dependency and does not run `tdd`, `edge-case-analysis`, `code-review` or `context-engineering`.
8. When any blocker remains, or the ready inputs still cannot pass the implementation gate without invention, an unrelated change or a speculative abstraction, write no file and apply no change from this attempt. Return one BLOCKED report with `Status: BLOCKED`, `Reason`, `Evidence`, `Missing prerequisite` and `Recommended next skill/action`, and name every missing prerequisite. `Evidence` cites the input for each blocker. Recommend the skill for the earliest blocker, in this order: missing project context, then a diagnosis whose root cause is not confirmed or an unknown failure, then a ticket problem, then a specification problem, then a decision problem, then an external fact or a research report that is present and not `ready`, then a ready specification that is not one bounded change, then a change that cannot stay smallest. When the inputs are ready and the gate still cannot pass without invention, an input that does not define the behaviour recommends `to-spec`; a ticket that is not independently executable recommends `to-tickets`; a fix that is not determined from a confirmed cause recommends `diagnose`; an open decision recommends `clarify`. Do not delete an existing report or test-evidence file.
9. Stop. When the report was written, report both paths, their status, whether the working tree changed, and whether `code-review` is authorized. A non-trivial ready change authorizes `code-review` and does not authorize another skill. A trivial ready change, clear and local with negligible risk, reports that `code-review` may be omitted and does not authorize another skill. When R12 or R14 applies, name `edge-case-analysis` or `docs` in Remaining Work as applicable and not invoked. When the requester did not ask for a step beyond the change, report that the result is `ready` and name the canonical consumer. Do not invoke `code-review`, `tdd`, `edge-case-analysis`, `docs`, `context-engineering` or any other skill. Do not write the glossary, `CONTEXT.md`, any other artifact, or extend ADR `0001`.

## Failure behaviour

Return the [contracted `BLOCKED` result](../../../contracts/failure.md) when any blocker remains or the implementation gate cannot pass without invention, an unrelated change or a speculative abstraction. Name every missing prerequisite. `Evidence` cites the input for each blocker. Recommend the earliest blocker: missing project context recommends `context-engineering`; a diagnosis whose root cause is not confirmed, or an unknown failure, recommends `diagnose`; a ticket problem recommends `to-tickets`; a specification problem recommends `to-spec`; a decision problem recommends `clarify`; an external fact or a research report that is present and not `ready` recommends `research`; a ready specification that is not one bounded change recommends `to-tickets`; a change that cannot stay smallest recommends the producer named in the workflow. Do not leave an implementation report, a test-evidence file or a code change from this attempt. Do not delete an existing report or test-evidence file. The files this skill writes are a ready implementation report and a ready test-evidence file. Never present the BLOCKED result as a ready implementation report.
